# Ralph-Loop Quality Review Methodology

이 스킬은 코드 변경에 대한 5회 반복 검증 방법론(Ralph-Loop)을 정의합니다.

## Ralph-Loop이란?

Ralph-Loop는 같은 코드를 5가지 서로 다른 관점에서 순차적으로 검증하는 체계적 코드 품질 검증 방법론입니다. 각 패스는 특정 관점에만 집중하여 인지 부하를 분산하고, 다각도 검증을 통해 이슈 누락을 최소화합니다.

```
Pass 1: 정확성 → Pass 2: 보안 → Pass 3: 성능 → Pass 4: 스타일 → Pass 5: 종합
```

## 검증 시작 전 준비

1. 변경된 파일 목록 확인 (`git diff --name-only` 또는 태스크 설명 참조)
2. 모든 변경 파일 읽기
3. 변경 컨텍스트 파악 (기능 추가/버그 수정/리팩토링/인프라)

## Pass 1: 코드 정확성 & 로직 오류

**핵심 질문**: "이 코드가 의도대로 동작하는가?"

### 체크 항목

| # | 항목 | 확인 방법 |
|---|------|-----------|
| 1.1 | 비즈니스 로직 일치 | 요구사항 대비 로직 흐름 추적 |
| 1.2 | 엣지 케이스 처리 | null, undefined, 빈 배열, 빈 문자열, 0, false |
| 1.3 | 에러 핸들링 | try-catch 범위, 에러 타입 구분, 에러 바운더리 |
| 1.4 | 비동기 처리 | await 누락, Promise.all 사용, race condition |
| 1.5 | 타입 안전성 | 타입 단언(as) 남용, any 타입, 타입 가드 |
| 1.6 | 조건문 로직 | off-by-one, 부정 조건, 복합 조건 |
| 1.7 | 데이터 변환 | 매핑 정확성, 필드 누락, 타입 변환 |
| 1.8 | Import/Export | 올바른 모듈, 순환 참조 |

## Pass 2: 보안 취약점 (OWASP Top 10)

**핵심 질문**: "이 코드에 보안 구멍이 있는가?"

### 체크 항목

| # | 항목 | 위험 패턴 |
|---|------|-----------|
| 2.1 | 인젝션 | 사용자 입력이 직접 쿼리/명령에 삽입 |
| 2.2 | XSS | `dangerouslySetInnerHTML`, 미이스케이프 출력 |
| 2.3 | 인증 결함 | 하드코딩 비밀, 약한 토큰 검증, 세션 관리 |
| 2.4 | 민감 데이터 노출 | 로그에 비밀번호, 응답에 내부 오류 상세 |
| 2.5 | 접근 제어 | 권한 검증 누락, IDOR |
| 2.6 | CORS 설정 | 과도한 origin 허용 |
| 2.7 | 의존성 취약점 | 알려진 취약 버전 |
| 2.8 | 환경 변수 | 하드코딩된 URL/비밀, .env 파일 커밋 |

## Pass 3: 성능 & 최적화

**핵심 질문**: "이 코드가 효율적으로 동작하는가?"

### 체크 항목

| # | 항목 | 위험 패턴 |
|---|------|-----------|
| 3.1 | 렌더링 성능 | 불필요한 리렌더링, 거대 컴포넌트 |
| 3.2 | 번들 크기 | 전체 라이브러리 import, tree-shaking 불가 |
| 3.3 | N+1 쿼리 | 루프 내 DB 쿼리, 미최적화 Prisma include |
| 3.4 | 캐싱 | 서버 데이터 캐싱 미활용, 클라이언트 캐시 |
| 3.5 | 이미지 | next/image 미사용, sizes 미설정 |
| 3.6 | 메모리 누수 | 이벤트 리스너 미해제, 구독 미해제 |
| 3.7 | 지연 로딩 | 대용량 컴포넌트 즉시 로딩 |
| 3.8 | API 호출 | 중복 호출, 불필요한 데이터 요청 |

## Pass 4: 코드 스타일 & 규칙 준수

**핵심 질문**: "이 코드가 프로젝트 규칙을 따르는가?"

### 체크 항목

| # | 항목 | 기준 |
|---|------|------|
| 4.1 | TypeScript | strict mode, 명시적 타입, no any |
| 4.2 | ESLint | 프로젝트 ESLint 규칙 준수 |
| 4.3 | 네이밍 | camelCase(변수/함수), PascalCase(컴포넌트/타입) |
| 4.4 | 컴포넌트 | 함수형만, 서버/클라이언트 적절 분리 |
| 4.5 | Tailwind | 유틸리티 클래스, 인라인 스타일 없음 |
| 4.6 | CDK | 스택 분리, 필수 태그, 환경 분리 |
| 4.7 | 이중 언어 | 커밋 메시지 일본어+한국어, 코멘트 |
| 4.8 | 파일 구조 | 프로젝트 디렉토리 규칙 준수 |

## Pass 5: 최종 종합 검토 & 판정

**핵심 질문**: "전체적으로 이 변경이 안전하게 통합될 수 있는가?"

### 수행 절차

1. **이슈 집계**: Pass 1~4의 모든 이슈를 심각도별 분류
2. **상호 영향 분석**: 이슈들 간의 연쇄 효과 확인
3. **리스크 평가**: 운영 환경 영향도 판단
4. **판정 결정**: 아래 기준에 따라 최종 판정

### 심각도 가이드

| 레벨 | 기준 | 예시 |
|------|------|------|
| **CRITICAL** | 운영 장애, 데이터 손실, 보안 침해 가능 | SQL 인젝션, 인증 우회, 무한 루프 |
| **WARNING** | 잠재적 문제, 성능 저하, 규칙 위반 | N+1 쿼리, any 타입 사용, 캐싱 미활용 |
| **INFO** | 개선 권장, 모범 사례 | 더 나은 네이밍, 리팩토링 제안 |

### 판정 기준표

| 판정 | CRITICAL | WARNING | 설명 |
|------|----------|---------|------|
| **PASS** | 0건 | 0~1건 | 안전하게 통합 가능 |
| **PASS WITH WARNINGS** | 0건 | 2건 | 통합 가능하나 개선 권장 |
| **FAIL** | 1건+ | 또는 3건+ | 수정 후 재검증 필요 |

## 보고서 출력 형식

각 Pass의 결과를 다음 형식으로 보고:

```markdown
### Pass N: [제목]
**결과**: ✅ 이상 없음 / ⚠️ 이슈 N건

| # | 심각도 | 파일:라인 | 설명 | 권장 조치 |
|---|--------|-----------|------|-----------|
```

최종 판정은 반드시 명확하게:
```markdown
### 최종 판정: **PASS** / **PASS WITH WARNINGS** / **FAIL**
```
